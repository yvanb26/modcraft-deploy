Optionnel

      

        
        
      


      

        RCON (whitelist automatique)
        

          
          
          
        

        
La whitelist automatique fonctionne directement sur un serveur en ligne (Online-mode coché). Sur un serveur hors ligne, la commande whitelist add inscrit le vrai UUID du compte Mojang alors que le serveur en calcule un autre à la connexion : l'API écrit donc elle-même whitelist.json (les deux UUID hors ligne du pseudo, casse exacte et minuscules) avec l'accès SFTP/FTP saisi pour ce serveur dans l'onglet « Serveur Minecraft » (rien à ressaisir ici : il est recopié automatiquement, dossier distant = dossier du serveur qui contient whitelist.json), puis fait un whitelist reload. Sans cet accès, la whitelist ne marche que pour un pseudo qui n'existe pas chez Mojang. Pensez à déployer servers.json sur l'API après modification.

1. Principe général

            
Cette app permet de configurer un serveur Node.js pour le launcher pas un serveur Minecraft : elle te permet de le personnaliser à l'image de ta communauté, et de garantir que seuls les membres de ta communauté y aient accès.

            
Cet outil et le launcher ont été conçus pour distribuer des modpacks "tout prêts" et les maintenir à jour automatiquement, sans aucune intervention de tes membres !

            
Le launcher, quant à lui, s'occupe d'installer les bonnes versions de Java, les loaders, et le bon client Minecraft d'après la version que tu as configurée dans l'onglet Serveurs. Le serveur Node.js écrit automatiquement, via des commandes RCON, dans la whitelist de chaque serveur (si le RCON est configuré).

            
Cette application garde toutes tes données dans le dossier ModCraft Deploy Admin de ton dossier utilisateur (créé automatiquement au premier lancement, conservé lors des mises à jour) : son sous-dossier api/ (le serveur) est : avec lui seul : ce qu'elle lit et modifie, et les serveurs Minecraft générés vont dans serveurs-minecraft/. Tu peux aussi importer un dossier api/ déjà existant pour conserver tous tes réglages/serveurs déjà configurés sur ton hébergement.

            

              Important : Les onglets Serveurs/Branding/Annonces écrivent directement dans api/ dès l'enregistrement, sans brouillon. C'est volontaire : ça permet de lancer un serveur de test. Pour publier ces changements sur le vrai serveur, il faut ensuite passer par l'onglet Déploiement.
            

            
Si api/ est introuvable au démarrage, un bouton « 🔧 Recréer le dossier api/ » apparaît et recrée les fichiers d'exemple complets à partir du modèle intégré à l'application.

3. Onglet Serveurs

            
Une carte = un serveur qui s'affiche dans le launcher (id, nom, description, bannière, adresse, version + loader).

            
Auto-connexion : case à cocher pour que le jeu rejoigne automatiquement ce serveur au lancement (arguments --server/--port). Activée par défaut.

            
Online-mode : à faire correspondre au réglage online-mode du vrai serveur Minecraft (fichier server.properties) : affiche côté joueur un badge avec infobulle à côté de la version, pour que le joueur sache tout de suite quel type de compte fonctionne sur ce serveur.

            
Modpack (optionnel) : laisse vide pour un serveur vanilla : le launcher installera juste le client, sans rien de plus. Pour les modpacks : choisis le dossier des fichiers, puis génère le manifest. L'avantage de ce launcher, c'est qu'il te permet de copier l'intégralité du dossier Minecraft que tu auras préalablement configuré sur ton PC : l'idéal est de copier les dossiers config/, mods/, shaderpacks/, resourcepacks/, et les fichiers options.txt et servers.dat.

            
🔒 Sécurité : seuls les formats réellement utilisés par Minecraft sont copiés lors de l'import (mods .jar, configs, textures, packs .zip...) : tout le reste, en particulier les exécutables, est automatiquement ignoré avec un message listant les fichiers rejetés. Côté joueur, le launcher lance aussi un scan Windows Defender après chaque téléchargement de nouveaux fichiers, avant d'autoriser le lancement du jeu.

            

              Attention : Évite de copier l'intégralité du dossier (même si rien ne t'en empêche) : tes joueurs se retrouveraient avec tout ce que tu as déjà généré et configuré, par exemple JourneyMap, ton UUID, ou tes touches clavier (keybinds).
            

            
Explication des différents dossiers et fichiers :

            
    
              
  • config/ : les fichiers de configuration des mods Minecraft.
    • 
              
  • mods/ : les mods installés pour le serveur.
    • 
              
  • shaderpacks/ : les packs de shaders utilisés.
    • 
              
  • resourcepacks/ : les packs de ressources utilisés.
    • 
              
  • options.txt : définit les options du client Minecraft et est lu à chaque lancement. Si, dans ton jeu, tu actives le narrateur, modifies des options graphiques, la langue, ou actives les shaders, c'est dans ce fichier que ça se passe. Ce fichier peut être important quand ton serveur utilise resourcepacks/shaderpacks à activer, puisqu'ils le seront par défaut si tu les actives dans le jeu : si tu modifies les touches du clavier, elles seront également copiées.
    • 
              
  • servers.dat : liste des serveurs connus par le client Minecraft. Quand tu ouvres ton jeu et ajoutes un serveur, il est enregistré dans ce fichier.
    • 
              
  • *.txt : certains mods écrivent leur config dans config/ ou directement à la racine du dossier de jeu, au format .txt. Comme pour options.txt, ça te permet de pré-configurer le mod avant même que le joueur y touche.
    • 
            

            
RCON (hôte/port/mot de passe) active la whitelist automatique : chaque joueur qui utilise le launcher y est ajouté automatiquement, sans intervention manuelle.

6. Onglet Déploiement

            
Une carte (SFTP, ou FTP / FTPS pour un hébergeur sans SFTP) vers le vrai serveur, avec 3 actions indépendantes, plus un diagnostic :

            
1. Mettre à jour le code : envoie src/, scripts/, package.json... sans JAMAIS toucher à data/ ni modpacks/. Sans danger, à relancer à chaque mise à jour du launcher/admin.

            

              À ne jamais oublier : Envoyer le code ne suffit pas : le serveur Node déjà en mémoire continue de tourner sur l'ancien code tant qu'il n'est pas redémarré depuis le panneau d'hébergement (PufferPanel ou équivalent).
            

            
2. Config : « Voir les différences » compare chaque fichier avant que « Déployer la config » n'écrase data/ + modpacks/ (fichiers déjà identiques ignorés automatiquement).

            
3. Fichiers individuels : envoie juste branding.json, news.json, ou servers.json + les modpacks qu'il référence (manifest régénéré, diff appliqué).

            
Diagnostic (SFTP) : « Voir le contenu distant » liste ce qu'il y a vraiment à l'emplacement configuré, avec la date de modification de chaque fichier : le plus rapide pour vérifier qu'un envoi a atteint le bon dossier.

          


          

            
7. Onglet Serveur Minecraft

            
Fabrique un serveur Minecraft prêt à l'emploi à partir d'un serveur déjà configuré dans l'onglet Serveurs : version, loader (Vanilla, Forge, Fabric, Quilt, NeoForge), modpack, mode de compte (online-mode), RCON et arguments Java. Le résultat est un dossier (et un zip) : jar ou installeur du loader, mods/ + config/, server.properties, eula.txt, jvm-args.txt et des scripts start-server.sh / start-server.bat.

            
Mods client / serveur : les mods « client uniquement » (OptiFine, JourneyMap…) doivent rester hors du serveur. L'outil en détecte une partie ; corrige le reste dans la liste (« Client uniquement » = exclu). Les dossiers resourcepacks/, shaderpacks/, optifine/ et les fichiers options*.txt sont toujours exclus.

            
EULA : coche la case pour écrire eula=true ; sinon le fichier contient eula=false et tu l'acceptes toi-même avant le premier démarrage.

            
Installer le loader maintenant : pour Forge, NeoForge et Quilt, lance l'installeur ici ; si aucun Java compatible n'est installé, l'outil télécharge automatiquement le bon (Eclipse Temurin, vérifié par SHA-256, dans son propre dossier : rien n'est installé sur votre système). Sinon, les scripts l'installent au premier démarrage (Internet requis).

            
Version de Java : un serveur ne tourne que sur certaines versions (Forge 1.7.10 à 1.12 : Java 8 uniquement). Les scripts start-server.bat / .sh cherchent eux-mêmes le Java qui convient parmi ceux installés ; JAVA_BIN permet d'en forcer un.

            
Envoi SFTP / FTP : session propre à chaque serveur Minecraft (protocole SFTP, FTP ou FTPS, hôte, port, compte, mot de passe et chemin distant, enregistrés chiffrés), distincte de celle de l'onglet Déploiement qui vise l'API du launcher ; un bouton teste la connexion. Les fichiers inchangés sont ignorés et rien n'est supprimé sur le serveur (le monde n'est jamais touché) ; la suppression des anciens mods de mods/ est optionnelle. Les fichiers de réglages déjà présents (server.properties…) sont conservés par défaut.

            

              Panels (PufferPanel, Pterodactyl…) : leur propre commande de démarrage remplace nos scripts : la commande exacte à saisir est écrite dans LISEZMOI-SERVEUR.txt et affichée après la génération. Le dossier généré n'est pas fait pour être lancé sur place : l'admin refuse d'écraser un dossier qui contient un monde.

1. General principle

            
This app lets you configure a Node.js server for the launcher not a Minecraft server: it lets you customize it to match your community's identity, and makes sure only your community's members can access it.

            
This tool and the launcher were built to distribute "ready-to-play" modpacks and keep them updated automatically, with zero effort from your members!

            
The launcher itself installs the right Java version, the right loader, and the right Minecraft client based on the version you configured in the Servers tab. The Node.js server automatically writes to each server's whitelist via RCON commands (if RCON is configured).

            
This application keeps all your data in the ModCraft Deploy Admin folder inside your user folder (created automatically on first launch, kept across updates): its api/ subfolder (the server) is the only thing it ever reads or modifies, and generated Minecraft servers go to serveurs-minecraft/. You can also import an existing api/ folder to keep all the settings/servers you already configured on your host.

            

              Important : The Servers/Branding/Announcements tabs write directly to api/ as soon as you save, no draft. That's intentional : it's what lets you run a local test server. To publish those changes to your real server, you then need to go through the Deployment tab.
            

            
If api/ can't be found on startup, a "🔧 Recreate the api/ folder" button appears and rebuilds a complete example setup from the template bundled with the app.

          


          

            
2. Dashboard

            
▶ Start / ⏹ Stop runs the launcher's test server (node src/index.js) directly from the selected api/ folder; logs stream into the console below.

            
📋 Copy launcher.config.json creates a copy of the config pointing at this local server : paste it into launcher.config.json to test the launcher LOCALLY against your changes, before applying them to the real server.

          


          

            
3. Servers tab

            
One card = one server shown in the launcher (id, name, description, banner, address, version + loader).

            
Auto-connect: checkbox so the game automatically joins this server on launch (--server/--port arguments). Enabled by default.

            
Online-mode: should match the online-mode setting of the real Minecraft server (server.properties) : shows the player a badge with a tooltip next to the version, so they immediately know which account type works on this server.

            
Modpack (optional) : leave blank for a vanilla server: the launcher will just install the client, nothing more. For modpacks: pick the files folder, then generate the manifest. The advantage of this launcher is that it lets you copy your entire, already-configured local Minecraft folder : ideally copy the config/, mods/, shaderpacks/, resourcepacks/ folders, and the options.txt/servers.dat files.

            
🔒 Security: only formats actually used by Minecraft are copied on import (mods .jar, configs, textures, .zip packs...) : everything else, executables especially, is automatically skipped with a message listing the rejected files. On the player's side, the launcher also runs a Windows Defender scan after downloading new files, before allowing the game to launch.

            

              Careful : Avoid copying the entire folder (even though nothing stops you): your players would end up with everything you've already generated and configured, e.g. JourneyMap, your UUID, or your keybinds.
            

            
What each folder/file is for:

            
    
              
  • config/: Minecraft mods' configuration files.
    • 
              
  • mods/: the mods installed for the server.
    • 
              
  • shaderpacks/: the shader packs used.
    • 
              
  • resourcepacks/: the resource packs used.
    • 
              
  • options.txt: defines the Minecraft client's options and is read on every launch. If, in your game, you enable the narrator, change graphics options/language, or enable shaders, that's what gets saved here. This file matters if your server ships with resourcepacks/shaderpacks meant to be on by default : enabling them in-game once will make it so, and keyboard rebinds get copied along too.
    • 
              
  • servers.dat: the list of servers known to the Minecraft client. Open your game, add a server, and it's saved here.
    • 
              
  • *.txt: some mods write their config to config/ or directly at the game folder's root, as .txt files. Just like options.txt, this lets you pre-configure the mod before a player even touches it.
    • 
            

            
RCON (host/port/password) enables the automatic whitelist: every player who uses the launcher gets added automatically, no manual work.

          


          

            
4. Branding tab

            
Identity: name, language, accent color, logo, background, window icon, custom CSS, music, site/Discord links.

            
Color theme: 7 colors for a full reskin, no code required.

            
Login: enable/disable free account, Ely.by, Microsoft (+ client ID) and Discord Rich Presence individually : also includes a single banner shared by all "Custom versions" (no per-install banner, since players create those themselves).

            
Easter egg: a free-form list of hidden zones (a corner of the window, or the copyright text) that each trigger a sound or a gif when clicked : add/remove as many entries as you like. Several entries on the same zone (a gif + an mp3) start together; an anti-spam ignores clicks while an easter egg is playing.

          


          

            
5. Announcements tab

            
"+ New announcement" opens a title/date/text form. The most recent one (first in the table) triggers the automatic popup on the launcher side if the player hasn't seen it yet.

          


          

            
6. Deployment tab

            
One card (SFTP, or FTP / FTPS for a host without SFTP) to the real server, with 3 independent actions, plus diagnostics:

            
1. Update the code : sends src/, scripts/, package.json... and NEVER touches data/ or modpacks/. Safe to run, re-run it after every launcher/admin update.

            

              Never forget : Sending the code isn't enough: the Node server already running in memory keeps executing the old code until it's restarted from your hosting panel (PufferPanel or similar).
            

            
2. Config : "View differences" compares every file before "Deploy config" overwrites data/ + modpacks/ (files that are already identical are skipped automatically).

            
3. Individual files : sends just branding.json, news.json, or servers.json + the modpacks it references (manifest regenerated, diff applied).

            
Diagnostics (SFTP) : "View remote content" lists what's actually at the configured location, with each file's last-modified date: the fastest way to confirm an upload actually reached the right folder.

          


          

            
7. Minecraft server tab

            
Builds a ready-to-run Minecraft server from a server already configured in the Servers tab: version, loader (Vanilla, Forge, Fabric, Quilt, NeoForge), modpack, account mode (online-mode), RCON and Java arguments. The result is a folder (and a zip): loader jar or installer, mods/ + config/, server.properties, eula.txt, jvm-args.txt and start-server.sh / start-server.bat scripts.

            
Client / server mods : "client only" mods (OptiFine, JourneyMap…) must stay off the server. The tool detects some of them; fix the rest in the list ("Client only" = excluded). resourcepacks/, shaderpacks/, optifine/ and options*.txt are always excluded.

            
EULA : tick the box to write eula=true; otherwise the file contains eula=false and you accept it yourself before the first start.

            
Install the loader now : for Forge, NeoForge and Quilt, runs the installer here; if no compatible Java is installed, the tool automatically downloads the right one (Eclipse Temurin, SHA-256 verified, into its own folder: nothing is installed on your system). Otherwise the scripts install it on first start (Internet required).

            
Java version : a server only runs on certain versions (Forge 1.7.10 to 1.12: Java 8 only). The start-server.bat / .sh scripts look for a suitable Java among the installed ones; JAVA_BIN forces a specific one.

            
SFTP / FTP upload : a session of its own for each Minecraft server (SFTP, FTP or FTPS protocol, host, port, account, password and remote path, stored encrypted), separate from the Deployment tab which targets the launcher API; a button tests the connection. Unchanged files are skipped and nothing is deleted on the server (the world is never touched); removing old mods from mods/ is optional. Existing settings files (server.properties…) are kept by default.

            

              Panels (PufferPanel, Pterodactyl…) : their own startup command replaces our scripts: the exact command to enter is written in LISEZMOI-SERVEUR.txt and shown after generation. The generated folder isn't meant to be run in place: the admin refuses to overwrite a folder that contains a world.
